# Редакторская обратная связь и теневой режим

Первый этап автоматизации (2026-10-27). Автоматических переводов, одобрений,
отклонений и публикаций здесь нет. Текущая рекомендация — детерминированная
база `shadow-rules-v1`, а не обученная модель и не проверка достоверности.

## Что сохраняется

Миграция `0005_editorial_events` добавляет журнал `editorial_events`.
Жизненный цикл остаётся в `news_items`. В журнал добавляются события:

- `collected`: исходный извлечённый текст, атрибуция и сведения о полноте;
- `draft_generated`: черновик после генерации, включая предыдущее состояние;
- `edited`: изменения редактора, значения до/после и текстовые diff;
- `translation_requested`: выбор для перевода, а не успешный перевод;
- `keypoints_requested`, `keypoints_generated`: запрос и результат генерации;
- `approved`, `rejected`, `bulk_rejected`: решения модератора;
- `system_updated`: прочие программные изменения редактируемых полей.

Каждая запись содержит статью и сюжет на момент действия, серверную идентичность
редактора, причину и комментарий, снимки состояний, хеши оригинала и черновика,
теневую рекомендацию до изменения, версию/хеш правил, конфигурацию моделей и
хеш исходного кода модельного конвейера. Конфигурация не означает, что все модели
вызывались в каждом событии. Секреты, Telegram initData и токены не сохраняются.
Глоссарий пока не настроен, это явно отражено в версии.

Снимок оригинала — доступный приложению извлечённый текст, не полный HTML сайта
и не попытка восстановить закрытый paywall-контент. Для старых статей первая
новая операция сохраняет доступное состояние; историю до обновления не выдумываем.

Запись правки/решения и обновление статьи выполняются в одной транзакции.
Ошибка журнала отменяет обновление. В затрагиваемых операциях используются
короткие блокировки строки; внешние API внутри этих транзакций не вызываются.
Поздний ответ AI не может вернуть отклонённую, опубликованную или поставленную
в очередь статью в статус processed. Открытые правки сохраняются перед одобрением.

Журнал append-only на уровне приложения: маршрутов изменения/удаления событий
нет. Это не криптографически защищённый журнал и не запрет изменений администратором
БД. Каскадного FK нет: обычное удаление новости сохраняет аудиторские снимки;
политика хранения/полного удаления данных должна учитывать журнал отдельно.

## Причины и пригодность данных

В карточке и редакторе доступны причины: интересный материал, первоисточник,
дубликат, мало новых фактов, неинтересно, устарело, непроверенные сведения,
неполный текст, ошибка факта/перевода/атрибуции, стиль, лимит и прочее.
Комментарий необязателен. Старые API-вызовы без причины работают и получают
`unspecified`; недопустимая причина отклоняется до изменения статьи.

`training_eligible` означает кандидата для последующей подготовки датасета,
а не уже проверенную обучающую пару:

- человеческий выбор для перевода и одобрение — положительные действия;
- отклонение и правка требуют содержательной причины;
- системные и демо-действия, массовые отклонения, лимит публикаций исключены;
- сохранение неизменённого текста не создаёт новую правку.

Telegram fallback также сохраняет идентичность редактора. В нём пока нет выбора
структурированных причин; отклонение с `unspecified` остаётся только в аудите.
Демонстрационное происхождение текста исключает пример независимо от actor.

## Теневой редактор

`shadow_recommendation()` учитывает имеющиеся признаки полноты текста,
английские маркеры слухов/обвинений, приоритет источника и тематическую релевантность.
Он предлагает `translate`, `skip` или `human_review`. Решение о публикации всегда
`human_review`, `automatic_actions=false`. Здесь нет LLM, дополнительных расходов,
автообновления промптов или обучения весов. Любая рекомендация может ошибаться;
она не оценивает истинность фактов и не ловит все языки/виды слухов.

Рекомендация в карточке пересчитывается по текущей версии правил. В журнале
замораживается рекомендация по состоянию до решения человека; следующие версии
не переписывают старые примеры. Это не доказательство, что человек видел конкретную
рекомендацию: событие не хранит телеметрию просмотра. При изменении поведения правил
нужно менять `POLICY_VERSION`; хеш кода дополнительно фиксирует реализацию.

На вкладке «Навучанне» показаны события, кандидаты и число сюжетов. Сравнение
отбора использует только явные решения по collected-статьям: выбор для перевода
и отклонения по причинам дубликата, новизны, интереса или актуальности.
`human_review` считается передачей редактору, не ошибкой и не совпадением.
Сравнение берёт сохранённую рекомендацию, а не результат после решения.
Это наблюдение за правилом отбора, не оценка фактов, перевода или готовности
к автопубликации. Показ рекомендаций может влиять на редактора; для честного
будущего эксперимента нужен также слепой/контрольный режим.

## API и локальная проверка

- `GET /admin/api/items/{id}/history?limit=20` — последние события (максимум 50).
- `GET /admin/api/editorial/summary` — агрегаты и варианты причин.
- `POST .../approve|reject|translate` принимает необязательные `reason_code`, `note`.
- `POST .../edit` принимает их вместе с редактируемыми полями.
- Все маршруты защищены существующей зависимостью Telegram admin.

Для демо: `uv run python scripts/demo_editorial.py`, затем
http://127.0.0.1:18080/admin. Используется SQLite в памяти, AI/получение оригинала
имитируются; Telegram publisher и collectors не запускаются. Перезапуск сбрасывает
демо. Автообновление очереди приостанавливается во время ввода и редактирования.

Для production сначала нужна миграция `alembic upgrade head` в процессе деплоя.
Локальный DB tunnel ведёт к production: обычные проверки выполняются на отдельной
тестовой SQLite; схему production этим этапом разработки не меняем.

## Следующий этап

Собрать разнообразные реальные решения, проверить разметку и восстановление
цепочки исходник → черновик → правки → одобрение. При подготовке датасета учитывать
слияния сюжетов, общие источники и время, чтобы один сюжет не попал в train и holdout.
После этого сравнить эту базу с подбором редакторских примеров и модельным отбором
на новых сюжетах. Автоперевод и публикация требуют отдельных этапов, проверок,
надёжных заданий и бюджета из общего плана автоматизации.
