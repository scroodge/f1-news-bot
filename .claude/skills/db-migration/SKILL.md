# Schema change via Alembic

Alembic owns the schema. `create_tables()` / `create_all` is for tests only —
never add it to a production path.

## Steps

1. **Edit the model** in `src/database.py`. If the field must flow through the
   app, also update the pydantic models in `src/models.py` and the
   `db_manager` methods that read/write it (e.g. `update_fields` and the
   row→model conversion).

2. **Write the revision by hand** — revisions use sequential 4-digit IDs, not
   autogenerated hashes. Find the latest:
   ```bash
   ls alembic/versions/
   ```
   Create `alembic/versions/NNNN_short_description.py` mirroring the existing style:
   ```python
   """Add foo column

   Revision ID: 0004
   Revises: 0003
   Create Date: YYYY-MM-DD

   """

   from collections.abc import Sequence

   import sqlalchemy as sa

   from alembic import op

   revision: str = "0004"
   down_revision: str | None = "0003"
   branch_labels: str | Sequence[str] | None = None
   depends_on: str | Sequence[str] | None = None


   def upgrade() -> None:
       op.add_column("news_items", sa.Column("foo", sa.Text(), nullable=True))


   def downgrade() -> None:
       op.drop_column("news_items", "foo")
   ```
   Always implement `downgrade()`. New columns on the existing table should be
   `nullable=True` or have a `server_default`, since production has rows.

3. **Keep it SQLite-compatible where tests touch it** — tests build the schema
   from models on `sqlite+aiosqlite://`, so model types must work on both
   (Postgres-only features belong in the migration).

4. **Verify**
   ```bash
   uv run ruff check . && uv run ruff format --check . && uv run pytest
   uv run alembic upgrade head --sql | tail -20   # offline: inspect generated DDL, no DB needed
   ```
   Applying for real locally needs the tunnel (`ssh -f -N -L 5433:localhost:5433 contabo`)
   and hits the **production** database — ask the user before running
   `uv run alembic upgrade head` locally. Normally migrations are applied
   during deploy (see the `deploy` skill).
